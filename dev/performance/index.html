Performance

Timings below are from an 8-core Windows machine with OpenBLAS, on randomly mated pedigrees with one record per animal and two fixed effects. Absolute times vary by up to ±40% between runs on this machine; ratios between methods are stable.

Fit times

fit_reml end to end, including all iterations, for each way of computing the traces the REML score needs (see The one hard term: traces via selected inversion):

animalsexact tracesHutchinson (50 probes)
1,0000.29 s0.12 s
2,5003.95 s0.28 s
5,00043.1 s1.03 s

Both agree on the variance components to three decimal places. The default, trace_method = :auto, uses the exact sweep for small problems and switches to Hutchinson probing above 20,000 nonzeros in the Cholesky factor.

Per-iteration split at q = 5000 (nnz(L) = 705k, fill 13.2×):

stagetime
MME assembly0.034 ms
numeric factorization19.5 ms
objective (assemble + factor + solve)21.5 ms
gradient + AI (Hutchinson, 50 probes)86 ms
gradient + AI (exact Takahashi)5164 ms

Pedigree setup is cheap: 50,000 animals take 72 ms for inbreeding and 14 ms for $\mathbf{A}^{-1}$.

Why this is faster than the R packages

Cross-validated against nadiv and sommer on identical pedigree datasets:

animalssommerAnimalModelsspeedup
4001.9 s0.042 s45×
80018.2 s0.26 s72×
2,000323.1 s2.99 s108×

The speedup grows with size, which tells you it is complexity, not constants. Three reasons, in order of importance.

1. Sparse $\mathbf{A}^{-1}$ versus dense $\mathbf{A}$. This is the big one. sommer's interface takes Gu = A — the relationship matrix itself, dense, $O(q^2)$ to store and $O(q^3)$ to factor. We take $\mathbf{A}^{-1}$, which is under 1% dense and getting sparser. The cost of one factorisation:

animalsdense $\mathbf{V}$-stylesparse MMEratio
4000.0069 s0.00029 s24×
8000.0874 s0.00093 s94×
1,6000.3236 s0.00255 s127×
2,0000.4283 s0.00346 s124×

That 24×→124× progression tracks the observed 45×→108× end-to-end speedup closely. The rest of the difference is everything below.

2. Factorisation reuse. We pay for fill-reducing analysis once per fit. A dense implementation has no symbolic phase to amortise, and re-does the full $O(q^3)$ decomposition every iteration.

3. Allocation discipline. Zero-allocation assembly, a cached selected inverse reused by both the score and the EM fallback, and preallocated multi-RHS buffers. R's copy-on-modify semantics make this pattern hard to achieve.

It is worth being clear about what is not the reason. The algorithms are the same ones ASReml and BLUPF90 use, and sommer implements AI-REML competently. Julia versus R matters far less than the data structure: an R package built on $\mathbf{A}^{-1}$ and sparse Cholesky (as pedigreemm (Vazquez et al., 2010) partly is, via lme4's sparse machinery) would close most of this gap. The lesson is about representation, not language.

Comparison with BLUPF90

sommer is not the toughest opposition, and it would be misleading to stop there. BLUPF90 (airemlf90) uses the same data structure and the same algorithms as this package — sparse $\mathbf{A}^{-1}$, AI-REML, FSPAK selected inversion (Pérez-Enciso et al., 1994) — so a comparison against it measures implementation quality on a level field:

animalsBLUPF90AnimalModelsratio
4000.182 s0.047 s3.9× faster
8000.202 s0.282 s1.4× slower
2,0000.517 s0.646 s1.25× slower

Roughly at parity: ahead on small pedigrees, slightly behind on larger ones. Variance components agree to 2e-5–2e-4 relative.

Getting here took two fixes worth recording, both found by measurement rather than reasoning.

The stopping rule was wasting half the iterations. It tested only the relative change in $\theta$, so a fit that had already converged kept going: at $q = 2000$ it ran 12 rounds with identical $\theta$ and $-2\log L$ from round 5 onward. Each of those no-op rounds paid for a full Takahashi sweep. Testing the scaled score before proposing a step, plus an objective-drop test after, cut it to 6 rounds for the same estimates.

Half the sweep's runtime was binary search. A ProfileToLLM table put _zget and its inlined comparison/shift operations at ~50% of total runtime. The cause: roughly half of all inner operations take the $k < i$ branch, each resolving a lookup by binary search averaging ~8 steps — 80 M search steps at $q = 2000$ for a factor with only 148 k nonzeros. Building a row-wise index of the result's lower triangle once, by counting sort in $O(\mathrm{nnz})$, makes that branch a single array read.

Where BLUPF90 is still ahead. It converges in 4 rounds to our 5–8, so its step control is better. Its per-iteration cost is also flatter with pedigree size, which points at FSPAK's selected inversion being a stronger implementation than the sweep here. Both are worth revisiting.

ASReml could not be tested: it is commercial software from VSN International, not on CRAN (verified), and requires a node-locked licence. If you hold one, bench/R/reference.R is generic over which R fitter it calls.

Reproducing the benchmarks

julia --project=bench bench/bench.jl      # timings and per-iteration profile
julia --project=bench bench/external.jl   # versus nadiv and sommer (needs R)
julia --project=bench bench/blupf90.jl    # versus BLUPF90 (see the file for binaries)

The R comparison needs install.packages(c("nadiv", "sommer")). The workflow_dispatch CI job reruns the R speed comparison and publishes the table as a job summary.
